# 01. 产品总览

> 需求前缀：`REQ-OV`  
> 代码基线：`main@3827590`  
> 文档性质：当前实现反向产品化整理

## 1. 背景

AI 开发工具和业务系统往往同时使用 OpenAI Responses、OpenAI Chat Completions、Anthropic Messages 以及 Images 等不同接口。不同上游服务即使声称兼容同一协议，也常在模型名、工具调用、Reasoning、流式事件、认证头和参数支持上存在差异。

如果客户端直接对接每个上游，通常会产生以下问题：

- 客户端需要分别管理多套 Base URL 和上游密钥；
- 不同协议之间无法复用同一客户端集成；
- 单个上游故障或限流会直接影响调用方；
- 多渠道优先级、容量和健康状态缺少统一调度；
- 普通用户与管理员之间缺少资源隔离；
- 请求、Token、成本、错误和流式时序难以统一观测；
- Codex CLI 等工具依赖的复杂工具调用和 SSE 语义容易在兼容服务上失真；
- 桌面使用者希望本机快速启动，而服务端部署又需要 PostgreSQL、Redis 和容器化能力。

OpenCodex 通过在客户端与上游 AI 服务之间增加统一代理和管理平面，集中解决上述问题。

## 2. 产品愿景

让用户可以用一个稳定的访问入口连接多个异构 AI 上游，并通过可视化管理台完成用户隔离、渠道配置、模型治理、可靠性控制和请求观测，而不要求调用方理解每个上游的协议差异。

## 3. 产品定位

OpenCodex 当前同时承担四类产品职责：

1. **统一协议网关**：正式支持 Responses、Chat、Messages 入口；代码中还暴露 Images 控制器契约，但生产实现和 DI 注册当前缺失；
2. **多渠道路由器**：按用户、模型、优先级、负载、亲和、容量和健康状态选择上游；
3. **AI 协议适配层**：转换请求、响应、SSE、工具、Reasoning、Usage 和多模态内容；
4. **管理与观测平台**：管理用户、访问 Key、渠道、模型、价格、搜索配置和请求日志。

## 4. 目标用户

| 用户 | 主要目标 | 核心价值 |
|---|---|---|
| 独立开发者 | 在本机或服务器统一接入多个模型服务 | 少改客户端配置、快速切换渠道、便于排障 |
| 团队超级管理员 | 管理多个用户及其上游资源 | 权限隔离、全局观测、集中模型和成本治理 |
| 团队普通用户 | 管理自己的渠道与访问 Key | 不接触他人配置，独立使用自己的上游资源 |
| API/CLI 调用方 | 用统一接口调用可用模型 | 协议兼容、故障转移、透明模型映射 |
| 运维人员 | 稳定部署、升级和监控服务 | Docker、PostgreSQL、Redis、健康检查和日志 |
| 测试与支持人员 | 重现协议、渠道、工具或流式问题 | 详细请求链路、尝试日志、原始与转换后正文 |

## 5. 产品目标

### 5.1 当前核心目标

| 编号 | 目标 | 成功定义 |
|---|---|---|
| G1 | 统一多协议入口 | 一个 OpenCodex 实例能接收 Responses、Chat、Messages 请求并路由到不同协议渠道 |
| G2 | 用户资源隔离 | 普通用户的渠道、访问 Key、路由候选和日志不与其他用户混用 |
| G3 | 提升调用可靠性 | 渠道故障、限流或容量满时按规则切换候选渠道 |
| G4 | 保留工具与流式语义 | 工具调用、Reasoning、Usage、finish reason 和 SSE 生命周期可跨协议转换 |
| G5 | 提供可运维管理面 | 用户可通过管理台完成配置、测试、日志查询和统计查看 |
| G6 | 支持本地与服务端形态 | 同一产品可作为 Tauri 桌面应用、单机 SQLite 服务或 PostgreSQL + Redis 服务运行 |
| G7 | 提供成本与问题定位依据 | 每个请求可记录 Token、成本、渠道尝试、错误和必要的请求响应详情 |

## 6. 非目标

以下能力不应被默认理解为当前产品范围：

- 不提供模型训练、微调或推理基础设施；
- 不提供上游账号购买、结算或余额充值；
- 不对上游模型输出质量做业务语义保证；
- 不承诺所有供应商私有字段都能无损跨协议转换；
- 不提供面向终端用户的对话产品或会话 UI；
- 不提供复杂组织架构、部门、项目空间或自定义 RBAC；
- 不提供外部身份提供商、SSO、OIDC 或 LDAP；
- 不提供完整 API 网关能力，如通用 WAF、配额套餐、计费出账和开发者门户；
- 不提供数据库跨地域复制或自动灾备；
- 不提供已完成的桌面自动更新、签名和公证体系；
- 不把历史重构计划中尚未实施的能力视为现行需求。

## 7. 核心使用场景

### 7.1 首次本地使用

1. 用户启动 Tauri 桌面应用或后端服务；
2. 系统发现尚未初始化；
3. 用户创建超级管理员；
4. 用户选择仅本地或局域网访问、配置端口和 Probe 拦截；
5. 系统保存设置并建立管理台登录态；
6. 桌面端在需要时重启 sidecar；
7. 用户进入管理台配置渠道和访问 Key。

### 7.2 团队管理员配置多用户

1. 超级管理员登录；
2. 创建普通用户；
3. 为自己配置渠道，或通过带 `owner_username` 的管理 API/导入为指定用户配置渠道；当前单渠道编辑 UI 未提供显式归属选择；
4. 为自己创建代理访问 Key；为指定用户创建时必须使用后端 `owner_user_id` 契约，当前前端提交 `owner_username` 的契约冲突需先修复；
5. 配置全局模型信息和价格；
6. 通过仪表盘和日志查看全局使用情况。

### 7.3 普通用户独立调用

1. 普通用户登录管理台；
2. 配置自己的一个或多个上游渠道；
3. 创建自己的 `ocx_...` 访问 Key；
4. 在 Codex CLI、SDK 或业务应用中配置 OpenCodex Base URL；
5. 请求只在该用户自己的启用渠道中路由；
6. 用户只能查询自己的请求日志和统计。

### 7.4 跨协议工具调用

1. Codex CLI 使用 Responses 协议提交带工具的流式请求；
2. 路由命中 Messages 或 Chat 渠道；
3. OpenCodex 规范化工具定义、工具历史和内容；
4. 请求被转换为渠道协议；
5. 上游流式工具调用被转换回 Responses SSE；
6. 客户端提交工具结果续轮；
7. OpenCodex 保持调用标识和历史配对。

### 7.5 渠道故障转移

1. 请求匹配多个候选渠道；
2. 系统优先选择亲和渠道或高优先级低负载渠道；
3. 渠道容量满、熔断或上游失败；
4. 若尚未向客户端写出流内容且错误允许转移，系统选择下一渠道；
5. 每次尝试单独记录日志；
6. 最终成功或返回统一错误。

### 7.6 排查失败请求

1. 用户从仪表盘实时错误列表进入详情，或在日志页筛选；
2. 查看主请求状态、模型、渠道、Token、成本和错误；
3. 查看渠道 attempt、OCR 子请求及会话关联字段；
4. 比较原始请求、上游请求、上游响应和客户端响应；
5. 查看原始/合并 SSE、Web Search 或 OCR 详情；
6. 根据证据调整渠道或兼容规则。

## 8. 产品原则

### 8.1 身份隔离优先

`REQ-OV-001`（MUST）：系统必须把管理台 Cookie 身份与代理 Bearer Key 身份视为两套独立认证体系，不得用管理台登录态替代代理访问 Key，也不得用访问 Key获得管理权限。

验收标准：

- 登录管理台后，不带 Bearer Key 调用 `/v1/responses` 仍应失败；
- 持有有效 Bearer Key 但没有管理 Cookie 时，不得访问 `/users`；
- 日志、渠道和模型路由使用访问 Key所属用户作为代理请求租户。

### 8.2 用户资源不跨租户兜底

`REQ-OV-002`（MUST）：普通用户没有可用渠道时，系统必须返回明确错误，不得自动使用超级管理员或其他用户渠道。

验收标准：

- 创建普通用户及有效访问 Key，但不创建渠道；
- 发起模型请求；
- 响应不得命中任何其他用户渠道，并返回无启用渠道的错误。

### 8.3 协议兼容不能掩盖不可表达语义

`REQ-OV-003`（MUST）：协议转换必须优先保持客户端可观察语义；确实无法等价表达的字段应按已定义的降级或错误规则处理，不得静默生成结构无效的请求。

验收标准：

- 3×3 协议矩阵中的每个支持方向均有结构测试；
- 不支持或不等价字段有明确保留、删除、转换或拒绝规则；
- 错误形态与入口协议兼容。

### 8.4 可靠性机制必须可解释

`REQ-OV-004`（MUST）：渠道选择、跳过、重试和故障转移必须能够通过日志或诊断信息解释，不得只返回最终失败而丢失尝试链路。

验收标准：

- 主请求可关联每个渠道 attempt；
- attempt 至少包含渠道、状态、耗时和错误摘要；
- 流首前故障转移与流首后不可转移能够被区分。

### 8.5 敏感信息最小暴露

`REQ-OV-005`（MUST）：管理台、API、日志和导出功能必须遵循统一的敏感信息展示策略。

当前状态：存在访问 Key 明文持久化、渠道 Key 返回和明文导出等冲突，需在风险文档中决策。

验收标准：

- 产品规则明确哪些凭证可再次查看、复制和导出；
- 日志不得泄露 Authorization、Cookie、密码或未授权的上游 Key；
- 普通用户不能读取其他用户凭证。

### 8.6 当前事实与未来目标分离

`REQ-OV-006`（MUST）：PRD、管理台文案和发布说明必须区分已实现能力、实验性能力、已知限制和未来计划。

验收标准：

- 尚未注册或未通过真实启动验证的链路不得宣称生产可用；
- 未确定的 SLA、RTO、RPO 使用 `TBD`；
- 历史方案文档不作为当前功能证据。

## 9. 版本范围

### 9.1 当前基线包含

- ASP.NET Core API 与静态管理台托管；
- Vue 3 + Element Plus 管理台；
- SQLite/PostgreSQL 双数据库；
- 可选 Redis 两级缓存与共享运行时状态；
- Tauri 2 桌面外壳和 .NET sidecar；
- 管理员/普通用户、访问 Key、渠道、模型目录、价格、Web Search、日志和统计；
- Responses、Chat、Messages 正式代理入口；Images 仅存在控制器/契约入口，当前生产实现与 DI 注册缺失；
- 协议转换、工具、流式、Reasoning、Usage、OCR 和 Web Search 特殊流程；
- xUnit 后端测试、少量 Node 前端状态测试；
- Docker 构建/部署制品和桌面发布工作流。

### 9.2 当前基线明确缺少或未完成

- 完整 RBAC 与审计操作日志；
- 全局登录限流、账户锁定和 CSRF Token；
- 深度 readiness；
- 日志保留、归档、配额和单条删除策略；
- 完整前端测试脚本、E2E 和 PR 质量门禁；
- 生产级桌面签名、公证和自动更新；
- 正式性能与容量指标；
- 完整备份恢复与自动回滚；
- Images 的 `IProxyImagesEndpointService` 生产实现、DI 注册及真实上游调用链。

### 10.1 可由当前系统直接度量的指标

| 指标 | 数据来源 | 说明 |

| 渠道活跃数 | 活跃渠道实时接口 | 当前主要用于运维观察 |

## 11. 依赖和假设

- 上游 AI 服务可通过 HTTP/HTTPS 访问，并提供至少一种已支持协议；
- 上游返回的 Usage、工具调用和 SSE 事件可能不完全标准，兼容规则只能覆盖已知差异；
- 调用方能够安全保存 OpenCodex 访问 Key；
- 管理员负责安全保存上游 Key 和数据库/Redis凭据；
- PostgreSQL + Redis 适用于多实例或更高并发，SQLite 主要面向单机；
- 桌面端用户允许应用启动本地 sidecar；
- 局域网访问需要额外网络和 TLS 防护，产品当前不会自动提供证书；
- 数据库迁移有足够权限在应用启动时执行；
- 日志存储可能包含敏感内容，部署方必须定义合规边界。
